# mi-pg

SQL-репозиторий объектов БД подсистемы MI для PostgreSQL / Postgres Pro.

Корпоративный GitLab является основным репозиторием разработки.

`main` содержит принятое и протестированное состояние проекта.

---

## Структура репозитория

```text
mi-pg/
├── ddl/
│   └── <module>/
│       ├── tables/
│       ├── sequences/
│       ├── views/
│       ├── packages/
│       ├── schemas/
│       ├── triggers/
│       ├── grants/
│       └── fill/
│
├── docs/
│   ├── baseline.md
│   ├── naming.md
│   └── workflow.md
│
├── .editorconfig
├── .gitignore
└── README.md
```

Создаются только те каталоги типов объектов, которые реально используются модулем.

## Основная модель разработки

Каждая Jira-задача разрабатывается в отдельной ветке.

```text
1 Jira = 1 branch = 1 Merge Request
```

Примеры:

```text
feat/WXXI-1234-email-search
fix/WXXI-1250-request-trigger
docs/update-workflow
invst/WXXI-1300-package-behavior
```

DDL попадает в `main` только после успешного тестирования.

Подробный процесс описан в [docs/workflow.md](docs/workflow.md).

## Исходники и поставка

Исходные SQL-файлы в GitLab хранятся в:

```text
UTF-8
```

Поставочные файлы для Update ядра формируются отдельно:

```text
GitLab source
UTF-8
     ↓
build / CI
     ↓
Windows-1251
     ↓
COMMENT ON + наша версия + {$Id$}
     ↓
SVN
```

GitLab остаётся источником истины.

SVN используется как часть delivery-процесса ядра и не является вторым репозиторием разработки.

Правила подробно описаны в [docs/naming.md](docs/naming.md).

## Базовые правила репозитория

В репозиторий не должны попадать:

- пароли и секреты;
- дампы БД;
- runtime-логи;
- клиентские данные;
- временные файлы разработки.

DDL по возможности должен быть безопасен для повторного выполнения, если это не меняет смысл операции.

Разрушающие изменения, например `DROP`, удаление колонок или ограничений, допускаются только как явная часть задачи и требуют внимательной проверки.
