# MI Development Workflow

## 1. Основной принцип

Корпоративный GitLab является основным репозиторием разработки.

Постоянная рабочая ветка одна:

```text
main
```

Для DDL действует правило:

> Изменение попадает в `main` только после успешного тестирования.

Постоянная ветка `dev` не используется.

Правила именования объектов, SQL-файлов, версий и поставочных артефактов описаны в `naming.md`.

---

# 2. Типы веток

Используются короткоживущие рабочие ветки:

```text
feat/*     — новая функциональность
fix/*      — исправление
docs/*     — самостоятельные изменения документации
invst/*    — исследование
release/*  — временная ветка релиза
```

Отдельный тип `hotfix/*` не используется.
Аварийное исправление также оформляется через `fix/*`; точка создания ветки определяется тем, какое состояние необходимо исправить.

## 2.1. Jira-задачи

Для функциональных изменений и исправлений действует правило:

```text
1 Jira = 1 branch = 1 Merge Request
```

Примеры:

```text
feat/WXXI-1234-email-search
fix/WXXI-1250-request-trigger
```

Рабочая ветка создаётся от актуального `main`:

```bash
git switch main
git pull --ff-only
git switch -c feat/WXXI-1234-short-purpose
```

## 2.2. Documentation branches

Самостоятельные изменения документации не требуют отдельной Jira-задачи.

Примеры:

```text
docs/update-workflow
docs/clarify-naming
docs/fix-readme
```

Для таких изменений используются обычные commit и Merge Request в `main`.

Пример commit:

```text
docs: clarify development workflow
```

Если документация меняется как часть конкретной Jira-задачи, отдельная `docs/*` ветка не создаётся.
Изменение документации выполняется в той же `feat/*` или `fix/*` ветке.

Пример:

```text
feat/WXXI-1234-email-search
├── DDL
└── связанное изменение документации
```

## 2.3. Investigation branches

`invst/*` используется для исследования и экспериментов.

Jira для такой ветки определяется контекстом работы.
Исследовательская ветка не обязана завершаться Merge Request.

Пример:

```text
invst/WXXI-1300-package-behavior
```

или для внутреннего исследования без Jira:

```text
invst/package-behavior
```

---

# 3. Разработка

Все изменения задачи выполняются внутри её ветки.

Можно делать столько commit и push, сколько необходимо:

```bash
git add <files>
git commit -m "WXXI-1234: short description"
git push
```

Неудачный тест не требует создания новой ветки.

Работа продолжается в той же ветке:

```text
изменение
   ↓
commit / push
   ↓
тест
   ├─ FAIL → исправление → commit / push → повторный тест
   └─ OK
```

Статусы Jira отражают этап работы, а не количество commit или push.

---

# 4. Синхронизация с main

Пока задача тестируется, `main` может измениться из-за других задач.

Перед финальным тестом рабочая ветка должна быть синхронизирована с актуальным `main`:

```bash
git fetch origin
git switch feat/WXXI-1234-short-purpose
git merge origin/main
```

После этого выполняется финальный тест.

Проверяется состояние:

```text
актуальный main
      +
изменение Jira-задачи
```

Если после синхронизации появились конфликты или изменилось поведение, выполняется повторное тестирование.

---

# 5. Merge Request

Для рабочей ветки создаётся Merge Request в `main`.

```text
feat/WXXI-1234-short-purpose
              ↓
             main
```

Рекомендуемое название:

```text
[WXXI-1234] Краткое описание изменения
```

Merge Request можно открыть заранее как Draft.

Пока тестирование не завершено, Merge Request не вливается в `main`.

После успешного финального теста:

```text
test OK
   ↓
Merge Request
   ↓
main
```

После merge рабочая ветка удаляется.

---

# 6. Что означает main

`main` содержит принятое состояние проекта.

```text
feature/fix branch
        =
разработка или тестирование

main
        =
изменение протестировано и принято
```

Прямые DDL-изменения в `main` не выполняются.

Изменения проходят через отдельную ветку и Merge Request.

---

# 7. Release branch

Отдельная постоянная ветка разработки не нужна.

Если необходимо зафиксировать конкретный набор уже готовых изменений для релизного тестирования, создаётся временная ветка:

```text
release/1.1.0
```

Она создаётся от нужной точки `main`.

После этого:

```text
main
 ├─ продолжает принимать новые готовые задачи
 │
 └─ release/1.1.0
        └─ хранит зафиксированный состав релиза
```

В `release/*` вносятся только исправления, необходимые для выпуска этого релиза.

Если в release-ветке появились исправления, они должны быть возвращены в `main`.

---

# 8. Tag

После успешного выпуска создаётся Git tag.

Пример:

```text
1.1.0
```

Tag фиксирует точное выпущенное состояние Git.

```text
release/*  → временная заморозка будущего релиза
tag        → постоянная отметка выпущенного состояния
```

После выпуска ветка `release/*` может быть удалена.

Tag остаётся.

---

# 9. Короткая схема

Обычная Jira-задача:

```text
Jira
 ↓
branch
 ↓
разработка
 ↓
тест
 ↓
синхронизация с main
 ↓
финальный test OK
 ↓
Merge Request
 ↓
main
```

Релиз:

```text
main
 ↓
release/*
 ↓
release test
 ↓
tag
```

---

# 10. Ответственность элементов

```text
Jira        — зачем выполняется функциональное изменение
feat/*      — новая функциональность по Jira
fix/*       — исправление по Jira
docs/*      — самостоятельная документация без обязательной Jira
invst/*     — исследование
branch      — место разработки изменения
commit      — история работы
MR          — контрольная точка перед main
main        — принятое состояние проекта
release/*   — временно зафиксированный состав релиза
tag         — точное выпущенное состояние
```

Подготовка Update для ядра, конвертация кодировки, именование поставочных файлов,
version comment и взаимодействие с SVN относятся к процессу delivery и должны
по возможности автоматизироваться средствами CI/Python.
