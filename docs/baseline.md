# Baseline объектов MI

## 1. Назначение

Документ описывает правила оформления, именования и версионирования объектов БД при первоначальном формировании поставки MI.

Baseline фиксирует исходное состояние объектов, с которого начинается их дальнейшее развитие в Git.

Для baseline не используются Jira, служебные обозначения `baseline`, `init`, `create` и другие дополнительные элементы в имени SQL-файла.

---

# 2. Версия baseline

Все объекты первоначальной загрузки считаются версией:

```text
1.0.1
```

Версия `1.0.1` является стартовой версией объекта в репозитории `mi-pg`.

После фиксации baseline дальнейшее изменение версии выполняется разработчиком самостоятельно.

---

# 3. Кодировка

Все исходные SQL-файлы baseline хранятся в:

```text
UTF-8
```

Windows-1251 в Git-репозитории не используется.

Если корпоративный механизм update требует Windows-1251, конвертация выполняется при подготовке поставочного артефакта.

Таким образом:

```text
Git / GitLab       -> UTF-8
Update             -> Windows-1251
```

---

# 4. Имя SQL-файла

Для baseline имя SQL-файла совпадает с именем объекта в БД.

Примеры:

```text
mi_req.sql
mi_rsp.sql
mi_person.sql
mi_log.sql

s_mi_req.sql
s_mi_rsp.sql

v_mi_req.sql
v_mi_person.sql

mi_logger.sql
mi_request_api.sql
```
---

# 5. Именование объектов БД

Именование объектов baseline должно соответствовать правилам `docs/naming.md`.

Основные форматы:

| Тип объекта | Формат |
|---|---|
| Table | `mi_<name>` |
| View | `v_mi_<name>` |
| PK Sequence | `s_<table>` |
| Other Sequence | `s_<table>__<column>` |
| Primary Key | `pk_<table>` |
| Foreign Key | `fk_<table>__<ref_table>[__<purpose>]` |
| Unique Constraint | `uk_<table>__<purpose>` |
| Check Constraint | `ck_<table>__<purpose>` |
| Index | `ix_<table>__<purpose>` |
| Unique Index | `ux_<table>__<purpose>` |
| Trigger | `t_<timing><operation>[_s]_<table>__<purpose>` |
| Trigger Function | `tf_<timing><operation>[_s]_<table>__<purpose>` |

Существующие объекты не переименовываются только ради приведения к новому стандарту без отдельного решения о миграции.

---

# 6. Служебный SQL-заголовок

Для baseline дополнительные служебные заголовки в SQL-файлы не добавляются.

Не требуется:

```sql
-- object:
-- jira:
-- version:
-- operation:
-- description:
```

Информация о назначении и версии объекта фиксируется непосредственно в комментарии PostgreSQL.

---

# 7. Комментарий к объекту

Каждый baseline-объект должен иметь PostgreSQL-комментарий.

Формат комментария:

```text
<Подсистема>. <Модуль>. <Описание объекта>. '$id: {<версия>} {<дата>} <пользователь>$'
```

Для baseline используется версия:

```text
1.0.1
```

Пример для MI:

```text
MI-edo. Реестр запросов. Таблица единого реестра. '$id: {1.0.1} {05.10.2026} Sulimoff$'
```

Состав комментария:

```text
Подсистема
Модуль
Описание объекта
Версия
Дата
Пользователь
```

---

# 8. Комментарий таблицы

Пример файла:

```text
mi_req.sql
```

Пример:

```sql
create table mi.mi_req
(
    ...
);

comment on table mi.mi_req is
$$Запросы внешних Систем. Реестр запросов. Таблица единого реестра. '$id: {1.0.1} {05.10.2026} Sulimoff$'$$;
```

Для строк с `$id` рекомендуется использовать dollar quoting:

```sql
$$...$$
```

Это позволяет не экранировать одинарные кавычки внутри комментария.

---

# 9. Комментарии других объектов

Аналогичный подход используется для других объектов, если PostgreSQL поддерживает `COMMENT ON` для соответствующего типа.

Например:

```sql
comment on sequence mi.s_mi_req is
$$Запросы внешних Систем. Реестр запросов. Последовательность идентификаторов запросов. '$id: {1.0.1} {05.10.2026} Sulimoff$'$$;
```

```sql
comment on view mi.v_mi_req is
$$Запросы внешних Систем. Реестр запросов. Представление реестра запросов. '$id: {1.0.1} {05.10.2026} Sulimoff$'$$;
```

Описание должно отражать назначение объекта, а не повторять только его техническое имя.

---

# 10. Packages

Для packages Postgres Pro версия может дополнительно храниться внутри самого объекта.

Пример:

```sql
cVersion CONSTANT varchar(100) :=
    '$id: {1.0.1} {05.10.2026} Sulimoff$';
```

Для существующих packages сохраняется сложившийся способ ведения версии.

Для baseline стартовая версия также принимается равной:

```text
1.0.1
```

---

# 11. Триггеры

Trigger и соответствующая trigger function хранятся в одном SQL-файле.

Имя файла совпадает с именем trigger.

Пример:

```text
t_bi_mi_req__validate.sql
```

Файл содержит:

1. создание или обновление trigger function;
2. создание trigger.

Trigger создаётся для таблицы в её схеме.

Trigger function создаётся в схеме функционального модуля.

Пример:

```text
Таблица:
mi.mi_req

Trigger:
t_bi_mi_req__validate

Trigger Function:
mi_request.tf_bi_mi_req__validate
```

# 13. Требования к baseline SQL

Baseline должен описывать исходное состояние объекта.

При подготовке baseline необходимо проверить:

1. SQL-файл находится в UTF-8.
2. Имя файла соответствует имени объекта.
3. Объект имеет корректное имя по правилам `naming.md` либо сохраняет существующее историческое имя.
4. Объект имеет PostgreSQL-комментарий.
5. В комментарии указана версия `1.0.1`.
6. В комментарии указаны дата и пользователь.
7. SQL успешно выполняется на тестовой БД.
8. По возможности повторное выполнение SQL не должно приводить к ошибкам или повреждению структуры.

---

# 14. Что не является baseline

Baseline не является историей всех прошлых изменений объекта.

Не требуется восстанавливать:

- старые Jira;
- старые версии;
- последовательность предыдущих ALTER;
- предыдущие релизы;
- старые update-файлы.

Baseline фиксирует текущее исходное состояние объекта на момент начала ведения нового репозитория.

---

# 15. Переход от baseline к истории изменений

После фиксации baseline дальнейшие изменения объектов выполняются отдельными SQL-файлами.

Например, baseline:

```text
mi_req.sql
```

Новая задача:

```text
mi_req__WXXI-1250__add_col__email__v1.0.2.sql
```

Следующее изменение:

```text
mi_req__WXXI-1270__create_index__ix_email__v1.0.3.sql
```

Таким образом:

```text
mi_req.sql
```

является стартовым состоянием объекта версии `1.0.1`, а все последующие SQL-файлы формируют историю его развития.

---

# 16. Первоначальная поставка

При первой поставке baseline используется для формирования начального update.

Исходные файлы:

```text
UTF-8
```

Поставочные файлы при необходимости преобразуются в:

```text
Windows-1251
```

Имя поставочного файла может совпадать с именем объекта:

```text
mi_req.sql
```

Префикс `c_` не является обязательным и используется только если этого требует конкретный формат корпоративного update.

---

# 17. Фиксация baseline

После подготовки и проверки baseline рекомендуется:

1. зафиксировать все baseline-файлы в Git;
2. проверить `git status`;
3. проверить тестовое применение;
4. сформировать первую alpha-поставку;
5. после успешной проверки поставить Git tag первой версии приложения.

После фиксации baseline его развитие выполняется через отдельные SQL-файлы изменений.

Основное правило:

> Baseline фиксирует исходное состояние объекта версии `1.0.1`. Дальнейшая история объекта формируется отдельными SQL-скриптами, связанными с Jira и версией объекта.
