# Правила именования SQL-скриптов MI

## 1. Общий принцип

Исходные SQL-скрипты хранятся отдельными файлами по логическим изменениям объектов БД.

**Один файл = одно логически законченное изменение.**

При этом один файл может содержать несколько взаимосвязанных SQL-команд, например `ALTER TABLE`, `COMMENT` и `CREATE INDEX`.

## 2. Формат имени файла

`<object>__<JIRA>__<operation>[__<parameters>]__v<version>.sql`

Состав имени:

| Элемент | Назначение |
|---|---|
| `object` | Имя изменяемого объекта |
| `JIRA` | Номер задачи в Jira |
| `operation` | Тип изменения |
| `parameters` | Уточнение операции (необязательно) |
| `version` | Версия объекта, назначенная разработчиком |

Смысловые части имени разделяются двойным подчёркиванием `__`.

Внутри отдельных частей допускается одинарное подчёркивание `_`.

## 3. Примеры именования

Создание таблицы:

`mi_req__WXXI-1000__create__v1.0.0.sql`

Добавление колонки:

`mi_req__WXXI-1234__add_col__email__v1.0.1.sql`

Изменение колонки:

`mi_req__WXXI-1235__alter_col__status__v1.0.2.sql`

Создание индекса:

`mi_req__WXXI-1236__create_index__ix_email__v1.0.3.sql`

Добавление ограничения:

`mi_req__WXXI-1237__add_constraint__chk_status__v1.1.0.sql`

Комплексное изменение:

`mi_req__WXXI-1250__change__email_search__v1.2.0.sql`

## 4. Допустимые операции

| Операция | Описание |
|---|---|
| `create` | Создание объекта |
| `add_col` | Добавление колонки |
| `alter_col` | Изменение колонки |
| `create_index` | Создание индекса |
| `add_constraint` | Добавление ограничения |
| `comment` | Изменение комментария |
| `grant` | Выдача прав |
| `change` | Несколько связанных изменений |
| `extend` | Комплексное расширение объекта |

Список операций может дополняться по мере развития проекта.

### Комплексные изменения

Если один скрипт содержит несколько связанных операций, используется `change` или `extend`.

Пример:

`mi_req__WXXI-1250__change__email_search__v1.2.0.sql`

Такой скрипт может одновременно:

- добавить колонку `email`;
- назначить комментарий;
- создать индекс `ix_email`.

Параметр `email_search` описывает назначение изменения, а не перечисляет все SQL-команды.

## 5. Версионирование объекта

Версию объекта ведёт разработчик самостоятельно.

Рекомендуемый формат:

`MAJOR.MINOR.PATCH`

Примеры: `1.0.0`, `1.0.1`, `1.1.0`, `2.0.0`.

Момент изменения версии и её значение определяет разработчик исходя из характера внесённых изменений.

Версия объекта не является порядковым номером SQL-файла и не заменяет версию релиза приложения.

Несколько файлов могут относиться к одной версии объекта.

## 6. Jira

Каждое изменение должно иметь ссылку на задачу Jira.

Номер Jira обязательно включается в имя SQL-файла.

Для сокращения ручной работы предусматривается генератор файлов, который получает номер Jira:

- из имени текущей Git-ветки;
- либо из локального параметра `git config --local mi.jira` (на этапе работы напрямую в `main`).

Номер Jira не определяет порядок выполнения SQL-скриптов.

## 7. Заголовок SQL-файла

Используется короткий заголовок:

    -- object: mi.mi_req, table
    -- jira: WXXI-1250
    -- version: 1.2.0
    -- operation: change email_search

Дополнительные поля не являются обязательными.

## 8. Кодировка

Все исходные SQL-файлы репозитория должны храниться в **UTF-8 без BOM**.

Поставочные SQL-артефакты формируются pipeline-ом в кодировке **Windows-1251**.

## 9. Порядок сборки

Порядок отображения файлов в каталоге и порядок их исполнения являются разными понятиями.

Pipeline должен:

1. Группировать исходные файлы по объекту.
2. Определять версии из имён файлов.
3. Сортировать версии по числовым компонентам, а не лексикографически.
4. Объединять скрипты в правильной последовательности.
5. Конвертировать результат в Windows-1251.

Если в одной версии несколько зависимых скриптов, порядок их выполнения должен быть указан явно либо операции необходимо объединить в один логический файл.

При неоднозначном порядке сборка должна завершаться ошибкой.

## 10. Имя поставочного файла

Для таблиц итоговое имя определяется корпоративным стандартом:

`<table_name>.sql`

Например, исходники:

- `mi_req__WXXI-1000__create__v1.0.0.sql`
- `mi_req__WXXI-1234__add_col__email__v1.0.1.sql`
- `mi_req__WXXI-1250__change__email_search__v1.2.0.sql`

После сборки образуют один поставочный файл:

**`mi_req.sql`**

Поставочные файлы являются результатом работы pipeline и не редактируются вручную.
